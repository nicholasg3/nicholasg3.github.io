Sixteen Automations That Run Without Me

I have sixteen jobs running on a schedule with nobody watching them. Here is what each one does, the eight rules I ended up writing after they misbehaved, and the four times they broke badly enough to change my mind about something.

By Nicholas Garcia — Lecturer, NUS School of Computing · Deputy Director, NUS FinTech Lab

Most posts about AI automation describe something the author did once, by hand, with a chat window open. This one is about things that ran last night and will run tonight whether or not I am paying attention.

That turns out to be a completely different engineering problem. A prompt you type is a tool. A job on a schedule is a system, and a system needs a kill switch, a test, a budget and somebody to blame.

All of this runs on one small virtual server plus a Mac with some scheduled jobs. There is no platform team. Most of it is Python from the standard library, cron, and a model called a handful of times a day. I am writing it up because people keep asking me what to automate first, and my honest answer is much duller than the demos.

Why I moved it off my laptop

The first decision that mattered had nothing to do with models.

I moved every scheduled job off my Mac and onto a small cloud server. Laptops are terrible hosts for automation: they sleep, they travel, they want you to unlock the screen before they will grant a permission, and mine had its disk synced by a file-sync client that will cheerfully corrupt a repository that a background process is halfway through writing.

The server is cheap and never sleeps. The jobs that genuinely need my physical machine — the ones driving a browser I am already logged into — stayed on the Mac, and those are now the exceptions I have to think about.

The second decision: the git repository is canonical, not the folder. My automation code used to live in a synced cloud folder. Two copies drifted, I edited both, and neither was right. Now the server holds the working copy, commits and pushes daily, and everything else pulls. I tarred up the old folder with a date in the filename and have not touched it since.

The sixteen jobs

1. A nightly worker that turns issues into pull requests

Every night at 2am an agent reads my issue tracker, picks up the low-priority items I have labelled for automation, and works them into pull requests. It cannot push to the main branch.

That last constraint is the whole design. The agent gets to write code; I merge it. The output is a diff I read over coffee, and the ones I do not like get closed at a cost of nothing but tokens.

If you copy one thing from this post: give the agent a queue it does not control, and an output boundary it cannot cross. The queue is the backlog, the boundary is the pull request.

2. A code reviewer that reads what actually runs

A nightly job builds a census of the code my server really executes. It reads the crontab and the service manager, follows references one level deep from those entry points, and ranks the files by how many live paths reach them. A second file records, per script, the commit at which it was last reviewed.

A file is due for review when it has commits newer than its last review. Priority is usage rank multiplied by staleness. The job reviews the top three files each night, one model call each, against a fixed rubric.

It fixes only what it can prove. If a file has a mechanical verifier — a syntax check, a nearby self-test, a dry-run mode — the job writes a minimal patch, applies it to a backup-protected copy and runs the verifier. If the verifier passes it commits and closes the issue. If it fails, the patch is reverted and the finding gets filed anyway, tagged as attempted. Everything else becomes an issue for the nightly worker in item 1, or for me.

The interesting part is not the model, it is the ranking. I cannot review everything, and a model reading random files is a waste. Rank by what runs, then by what changed.

3. A monthly security check with no model in it

Once a month a script checks six things: that my credential files are readable only by me, that nothing secret-shaped has landed in a commit in the last month, that every listening port is on an allowlist, that the pages behind authentication are still behind authentication, how many security updates are pending, and that password and root SSH logins are still off.

Zero model calls. Every check is a regex or a system command, so it is free, fast and identical every time.

I originally wrote it to run daily and that was a mistake. These checks barely change. A report that is identical thirty times a month stops being read, which means you skim the one that is different too. Monthly, it is an event, and I read it. The one test I care most about asserts that the report does not contain the token it found.

4. A weekly chronicler that turns exhaust into a record

Sunday evening, a job collects the week's commits, run logs and memos into a durable record, then nominates the handful of things worth writing about later. It never publishes anything.

The clever bit is capture, not synthesis. I can drop a [chronicle] marker into any commit message, and there is a one-line command that appends a note from wherever I am. Tagging costs two seconds at the moment something interesting happens. Synthesis happens on Sunday, by which point I would otherwise have forgotten all of it.

I did this backwards for about a year, trying to remember on Friday what Tuesday had been about.

5. An orchestrator that proposes its own work

A daemon watches for signals — stale logs, open items in a citations file, issues waiting for an agent, escalations from other jobs — scores them, and proposes small bounded projects. Then it sorts each one into a tier.

Tier What happens How something lands here
A It just runs There is a command whose exit code proves it worked.
B Opens an issue, sends one line to my phone Someone has to judge it. No mechanical proof available.
C Never happens Publishing, sending mail, touching secrets, deleting things.

I use that test constantly now, well beyond this daemon. "Is there a cheap mechanical check that proves this worked?" answers the autonomy question for almost anything. If yes, let it run. If no, the job is to prepare my decision, not to make it.

Tier C is implemented as a missing capability rather than a blocked one: the daemon can only propose projects that exist in its config file, and no template there publishes, mails or deletes. A job cannot decide to do something it has no vocabulary for.

6. A contacts database that started as a read-only report

A local SQLite database links the people in my directory to their email addresses, phone numbers and profiles, and to the threads I have actually had with them. It refreshes every morning.

Version one did exactly one thing: print how much of the directory had a usable channel, and where the gaps were. Read-only, no network writes, safe to run a hundred times. It told me my coverage was 2.5%, which was both embarrassing and precisely what I needed to know before building anything on top of that data.

Everything else got added afterwards, one tested phase at a time, with acceptance tests written mostly as prohibitions. Of 118 suggested matches I reviewed by hand, I rejected 38. That rejection rate is the reason nothing fuzzy is ever applied automatically.

7. A monitor for things that stopped happening

One scheduled job flags email threads that have gone quiet — messages I received, did not answer, and have now aged past a threshold.

Most alerting watches for events. The expensive failures in a personal system are absences: the reply you never sent, the job that silently stopped running, the invoice nobody chased. Watching for absence is harder to build and worth considerably more.

8. An offline mirror of my notes

My notes and databases live in a hosted tool. A job mirrors the whole workspace to plain markdown on disk — roughly a thousand pages across a couple of dozen databases — so agents can read it cheaply without hammering an API.

I got burned by this once and now have a rule written down: the mirror is a snapshot, not the truth. When currency matters, go to the live API. A stale mirror that looks authoritative is worse than no mirror.

9. My phone as the approval queue

Every job that needs a human decision sends one line to a private chat channel with the context and the options, and I answer there. The same channel is a bridge to a coding agent on the server, locked to my account, so I can drive the whole thing from a train.

Put the decision where you already are. An approval queue on a dashboard nobody opens is not an approval queue, it is a backlog.

10. A public page that expires its own contents

My public profile carries a list of opportunities I am circulating for other people. Each entry in a small YAML file has a deadline, and a daily scheduled action re-renders the page and drops anything past its date.

I add an entry and forget about it. The system forgets it too, on time. Putting expiry in the data is the cheapest maintenance strategy I know.

11. Automatic failover between model providers

A small daemon watches my usage against my subscription's rate window. At 80% it routes through a metered provider instead, and when the window resets it switches back.

I packaged this one up and put it on PyPI, because the problem is not remotely personal — anyone running agents on a subscription hits the same wall halfway through a task.

The general pattern is graceful degradation: your automation should have a worse-but-working mode and should enter it by itself.

12. A publishing gate that blocks my own agents

Nothing reaches this site until two artifacts exist: a grounding brief mapping every load-bearing claim to a source somebody actually checked, and a recorded score from a detector that flags machine-sounding prose. The checklist gets appended to the brief with dates. No checklist, no publication.

If you let agents write under your name, the quality gate has to be mechanical and has to sit in front of the publish step. Good intentions afterwards do not work; I have the takedown to prove it (item 3 in the failures below).

13. Heartbeats and backups

A heartbeat job reports that each machine is alive. A backup bridge copies what matters off the machine holding it. Both are boring and both have caught real problems. The heartbeat has also produced spectacular false alarms, which is its own story below.

14. An org chart, with an escalation path

Around job number eight I lost track of what everything was for. So each job now has a title, a manager and a one-sentence charter in a version-controlled JSON file: Chief of Staff, Managing Editor, Creative Director, Knowledge Gardener, Fleet Health Officer, Cost Controller and so on.

The part that earns its keep is the asks ledger. A role that hits a decision it cannot make files one question — one sentence, 400 characters, addressed to its manager by default — and carries on without blocking. A sweep twice a day moves anything unanswered for 48 hours one level up the chart. When it reaches me, I get a Telegram line.

I get fewer questions than I would with a flat design, and the ones I get are the ones nobody else could answer. The chart, the CLI, and the status bug that told me seven of ten employees were broken is its own post.

15. Two memory stores that may not overlap

One store holds rules: one file per lesson, a trigger and a rule and required evidence, capped at 50 active files, promoted only by a human. The other holds episodes — what happened, what was decided, why.

The episodic store's write gate rejects rule-shaped input and points it at the other store. Without that gate the two converge within weeks and the curated one stops being the authority on anything. Longer version here.

16. A weekly job that looks at the other jobs

The last one exists only to read the others — their logs, their escalations, their skipped runs — and propose changes.

It also reads its own session transcripts, which is a trick worth stealing: coding agents already write every message, tool call and error to disk, so the friction log you need already exists. That loop is written up separately — one change per cycle, gated on a runnable check, and it halts itself when the changes stop helping.

A fleet this size develops problems no individual job can see: two of them fighting over the same file, one that has silently skipped every run since a refactor, three sending nearly identical notifications at 8am.

Eight rules I wrote after things went wrong

None of these are theory. Each one exists because something misbehaved, and they now apply to every scheduled job I add.

  1. Observe and propose, never act. A job reads, analyses and files findings. It does not edit code outside its own directory, send outward communication, or spend money. Fixes go through the issue tracker where a human or the nightly worker picks them up.
  2. Exactly two kinds of output: an issue and a report. Capped at five new issues per run, with a duplicate search first. A job that can produce arbitrary output produces noise, and noise is how you stop reading your own system.
  3. The kill switch is one file. A file called STOPPED in the job's directory makes every entry point exit immediately and successfully. No flags, no config change, no redeploy. At midnight you want one command.
  4. A self-test has to pass before anything gets a schedule. Hermetic — no model calls, no network writes. If it cannot prove itself in a sandbox it does not get a cron line.
  5. Installers are idempotent and take a lock. Several jobs install their own schedules. Unlocked read-modify-write on a shared crontab loses entries, quietly. Use a file lock.
  6. No model call where parsing will do. The infrastructure checks have zero. The jobs that do use a model name it, carry a per-run cost cap and log what the run actually cost.
  7. Never git add -A. This is the single most dangerous line in an automated repository, because other daemons keep the working tree dirty. Each job commits only its own paths, rebases before pushing, retries once, then stops and logs.
  8. Write down state against signal. Every job carries a small table of failure modes. A signal arriving in a state nobody enumerated is how the first half-dozen bugs in my system happened: the message that came in during quiet hours, the directive that arrived while the queue was empty, the heartbeat that fired during a reboot.

Four things that broke

An inventory with no failures in it is marketing. These are the four that changed my rules.

A refactor deleted the scripts a running loop depended on. The loop did not stop. It crash-looped for about seven hours overnight, burning budget and filling the logs. Nothing checked that the thing it was about to execute still existed. The fix was not a smarter loop — it was a pre-flight existence check and a crash-loop counter that trips the kill switch.

A scheduler starved its own priority work. Items I had explicitly marked as directives kept losing to routine scoring, so the urgent work never ran. The fix was an additive priority boost instead of a multiplicative one, plus a manual override that ignores quiet hours — in both the gate that checks the schedule and the gate that checks the cycle. I only fixed one of those the first time, which is a very ordinary way to ship half a fix.

A draft went live because static hosts do not have staging. I published to GitHub Pages and assumed an unlisted page was a private page. It is not. Anyone with the URL can read it, and a catalogue link makes the URL public. I had to do an emergency takedown. There is now a CI check that fails any push putting a hidden page in the published directory, drafts live behind a gate in a different directory, and I am not allowed to weaken the check to make a build pass — only to move the content.

A network change gave me 42 hours of false alarms. A routing redirect I had added for convenience started intercepting connections and hanging them. Every remote check timed out and my monitoring reported half my machines as down. They were fine the entire time. The redirect is gone and there is a note explaining why it must not come back. False negatives make you miss outages; false positives make you stop believing your monitors, which is worse.

What I would build first

If you want to start, the order matters more than the tooling.

  1. One read-only report, on a schedule, delivered where you already look. Coverage gaps in your contacts, unanswered messages older than a week, subscriptions renewing next month. No writes. It will be wrong at first, and finding that out is the point.
  2. One queue with a boundary. A list of small tasks the agent may work on and a place it has to stop — a pull request, a draft, an item in an inbox. Do not let your first automation both decide and act.
  3. One deterministic check, monthly. Permissions, expiries, backups, listening ports. No model. It will still be correct in a year, when the fashionable parts have been rewritten twice.

After that, apply the tier test to everything you are tempted to automate. If a cheap mechanical check can prove the result, let it run unattended. If not, have it prepare the decision and put it on your phone. Nearly every bad automation I have built broke that one line, and nearly every good one respects it.

Three of these in depth

Each of these takes one item above and goes into enough detail to build your own version — the data structures, the caps, the rules that took real failures to discover.

  • I Gave My Agents an Org Chart — job titles and reporting lines in a JSON file, a CLI for asking your manager a question, the 48-hour escalation sweep, and why a role that finds problems is a role doing its job.
  • The Bot That Reads Its Own Transcripts — mining friction out of an assistant's own session logs, one change per cycle, gating on a runnable check, and a ledger that lets the loop halt itself.
  • Two Memory Stores That Are Not Allowed to Overlap — rules versus episodes, a cap of 50, manual promotion, contradiction checks, and the write gate that keeps one out of the other.

Everything here is a system I run myself. I have left out anything touching my employer's mail, my finances, or work that has not shipped yet.
