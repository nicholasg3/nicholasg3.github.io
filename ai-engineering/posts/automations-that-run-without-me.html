16 scheduled jobs run without supervision

An inventory of the AI agents that run on one small server and a Mac, the eight rules that govern them and the four failures that produced those rules.

By Nicholas Garcia — Lecturer, NUS School of Computing · Deputy Director, NUS FinTech Lab

Sixteen automated jobs now run on a schedule across one small cloud server and a Mac, with no person watching them. They review code, audit security, track costs, file issues, draft reports and escalate questions.

The infrastructure is ordinary. Most of the code is Python from the standard library. The scheduler is cron. A language model is called a few times a day. There is no platform team.

The engineering problem is not the model. A prompt typed into a chat window is a tool. A job on a schedule is a system, and a system needs a kill switch, a test, a spending limit and a defined owner.

This is the inventory, followed by the operating rules and the incidents behind them.

The server decision came first

Every scheduled job moved off the laptop to a cloud server early on. That decision had nothing to do with AI.

Laptops sleep. They travel. They require a screen unlock before granting a system permission. The Mac's disk was also synchronized by a cloud file client, which can corrupt a repository that a background process is writing.

The server does not sleep and holds its own credentials. Jobs that require the physical machine stayed on the Mac. Those are the ones that drive a browser session that is already logged in.

A second decision followed: the Git repository is authoritative, not the folder. Two copies of the automation code had drifted apart in a synchronized cloud folder, and neither was correct. The server now holds the working copy, commits and pushes daily, and every other machine pulls. The old folder was archived as a dated compressed file and is no longer edited.

The inventory

1. Issues to pull requests

An agent runs at 2 a.m. It reads the issue tracker, selects low-priority items labeled for automation and works them into pull requests. It cannot push to the main branch.

That restriction is the design. The agent writes code; a person merges it. Rejected work costs nothing but tokens.

The pattern generalizes: give an agent a queue it does not control and an output boundary it cannot cross. The queue is the backlog. The boundary is the pull request.

2. A code reviewer ranked by usage

A nightly job builds a census of the code the server actually executes. It reads the crontab and the service manager, follows references one level deep from those entry points and ranks files by how many live paths reach them.

A second file records the commit at which each script was last reviewed. A file is due when it has commits newer than that review. Priority is usage rank multiplied by staleness.

The job reviews the three highest-priority files each night, one model call each, against a fixed list of six defect categories.

It repairs only what it can verify. If a file has a mechanical check — a syntax test, a nearby self-test, a dry-run mode — the job writes a minimal patch, applies it to a backed-up copy and runs the check. A passing check produces a commit and a closed issue. A failing check reverts the patch and files the finding, marked as attempted.

3. A monthly security audit with no model

A script runs on the first of each month and checks six things: that credential files are readable only by their owner, that no secret-shaped string entered a commit in the past month, that every listening port appears on an approved list, that authenticated pages remain authenticated, how many security updates are pending, and that password and root remote logins are disabled.

There are no model calls. Every check is a regular expression or a system command, so results are identical when nothing changes.

The job originally ran daily. That was a mistake. The checks rarely change, and a report that is identical 30 times a month stops being read. Monthly, it gets read. A message reaches the operator's phone only when a check fails.

One rule governs the output: the report names a file and a line number, never the secret it found. A scanner that copies secrets into its own report creates a second, less protected copy of every secret on the machine.

4. A weekly record of operational exhaust

A job runs Sunday evening. It collects the week's commits, run logs and memos into a durable record, then nominates the few items worth writing about later. It publishes nothing.

Capture, not synthesis, is the working part. A marker dropped into any commit message tags an event as it happens, and a one-line command appends a note from anywhere. Tagging costs two seconds at the moment of interest. Synthesis waits for Sunday.

5. A daemon that proposes its own work

A daemon watches for signals: stale logs, open items in a citation file, issues awaiting an agent, escalations from other jobs. It scores them, proposes small bounded projects and sorts each into a tier.

Tier Action Admission test
A Runs unattended A command exists whose exit code proves the result.
B Opens an issue and sends one message to a phone A person must judge the outcome.
C Never runs Publishing, sending mail, handling secrets, deleting data.

The tier test applies well beyond this daemon: is there a cheap mechanical check that proves the task worked? If so, the task can run unattended. If not, the task prepares a decision rather than making one.

Tier C is enforced as a missing capability rather than a blocked one. The daemon can propose only projects that exist in its configuration file, and no template there publishes, mails or deletes. A job cannot choose to do something it has no vocabulary for.

6. A contacts database that began read-only

A local database links the people in a directory to their email addresses, phone numbers and profiles, and to the threads associated with them. It refreshes each morning.

The first version did one thing: report how much of the directory had a usable contact channel and where the gaps were. It made no writes. Coverage was 2.5%, a figure that had to be known before anything was built on that data.

Later phases each shipped with acceptance tests, most written as prohibitions. Of 118 suggested identity matches reviewed by hand, 38 were rejected. That rejection rate is why no probabilistic match is applied automatically.

7. A monitor for events that stopped

One job flags email threads that have gone quiet — messages received, not answered and now past a threshold.

Most alerting watches for events. The costly failures in a personal system are absences: the reply never sent, the job that silently stopped, the invoice never chased. Monitoring for absence is harder to build and worth more.

8. An offline mirror of the notes system

Notes and databases live in a hosted tool. A job mirrors the workspace to plain text files on disk, roughly 1,000 pages across about two dozen databases, so agents can read it without repeatedly calling an interface.

One rule governs the mirror: it is a snapshot, not the truth. When currency matters, the job queries the live service. A stale mirror that appears authoritative is worse than no mirror.

9. The phone as approval queue

Every job that requires a human decision sends one line to a private chat channel with the context and the options. The same channel bridges to a coding agent on the server and is restricted to a single account.

An approval queue on a dashboard nobody opens is not a queue. It is a backlog.

10. A public page that expires its own entries

A public profile page lists opportunities circulated for other people. Each entry carries a deadline in a small data file. A daily scheduled action rebuilds the page and drops anything past its date.

Expiry stored in the data is the cheapest maintenance available. Anything published with a natural end date should carry that date in its record.

11. Automatic failover between model providers

A daemon tracks usage against a subscription's rate window. At 80% it routes traffic through a metered provider. When the window resets it switches back.

The tool was packaged and published to the Python package index, because the problem is general. Anyone running agents on a subscription reaches the same limit partway through a task.

The pattern is graceful degradation. An automated system should have a reduced but working mode and should enter it on its own.

12. A publishing gate

Nothing reaches this site until two documents exist: a grounding brief mapping every load-bearing claim to a verified source, and a recorded score from a detector that flags machine-sounding prose. A dated checklist is appended to the brief. Without the checklist, there is no publication.

When agents write under a person's name, the quality gate has to be mechanical and has to sit before the publishing step.

13. Heartbeats and backups

A heartbeat job confirms each machine is running. A backup bridge copies critical data off the machine that holds it. Both have caught real failures. The heartbeat has also produced false alarms, described below.

14. An org chart with an escalation path

Each job carries a title, a manager and a one-sentence charter in a version-controlled file. The titles include chief of staff, managing editor, creative director, knowledge gardener, fleet health officer and cost controller.

The mechanism that earns its place is the questions ledger. A role that reaches a decision it cannot make files one question — a single sentence, 400 characters, addressed to its manager by default — and continues working. A sweep twice a day moves anything unanswered for 48 hours one level up the chart. Questions that reach the top generate a phone message.

The result is fewer questions than a flat design produces, and the ones that arrive are the ones nobody else could answer. Full description of the chart, the command-line tool and the status bug it exposed.

15. Two memory stores kept separate

One store holds rules: one file per lesson, each with a trigger, a rule and required evidence, capped at 50 active files and promoted only by a person. The other holds episodes — what happened, what was decided and why.

The episodic store's write gate rejects rule-shaped input and redirects it to the other store. Without that gate the two converge within weeks, and the curated store stops being authoritative. Full description.

16. A weekly review of the other jobs

The last job reads the others — their logs, their escalations, their skipped runs — and proposes changes.

It also reads its own session transcripts. Coding agents already write every message, tool call and error to disk, so the record of friction already exists. That loop is described separately: one change per cycle, gated on a runnable check, halting itself when the changes stop helping.

A group of this size develops problems no single job can detect: two jobs contending for the same file, one that has skipped every run since a refactor, three sending nearly identical notifications at 8 a.m.

Eight operating rules

Each rule followed an incident. All apply to every scheduled job.

  1. Observe and propose, do not act. A job reads, analyzes and files findings. It does not edit code outside its own directory, send outward communication or spend money. Fixes move through the issue tracker.
  2. Two kinds of output only: an issue and a report. Capped at five new issues per run, with a duplicate search first. A job that can produce arbitrary output produces noise.
  3. The kill switch is one file. A file named STOPPED in a job's directory makes every entry point exit immediately and successfully. No flags, no configuration change, no redeployment.
  4. A self-test must pass before a job gets a schedule. No model calls, no network writes. A job that cannot verify itself in a sandbox does not get a cron entry.
  5. Installers are idempotent and take a lock. Several jobs install their own schedules. Unlocked edits to a shared crontab silently lose entries.
  6. No model call where parsing is sufficient. The infrastructure checks use none. Jobs that use a model name it, carry a per-run spending limit and log what the run cost.
  7. Never stage all changes at once. A blanket "add all" commit is the most dangerous line in an automated repository, because other jobs keep the working tree modified. Each job commits only its own paths.
  8. Document state against signal. Each job carries a table of failure modes. A signal arriving in an unlisted state produced the first several bugs in this system.

Four failures

A refactor deleted the scripts a running loop depended on. The loop did not stop. It crash-looped for about seven hours overnight, consuming budget and filling logs. Nothing verified that the target still existed. The fix was a pre-flight existence check and a crash-loop counter that triggers the kill switch.

A scheduler starved its own priority work. Items marked as directives lost to routine scoring, so urgent work never ran. The fix was an additive priority increase rather than a multiplicative one, plus a manual override that ignores quiet hours in both the schedule gate and the cycle gate. Only one gate was corrected on the first attempt.

A draft page went live because static hosts have no staging. An unlisted page on a static host is not private. Anyone with the address can read it, and a catalog link makes the address public. An emergency removal followed. A continuous integration check now fails any change that places a hidden page in the published directory.

A network change produced 42 hours of false alarms. A routing redirect began intercepting connections and holding them open. Remote checks timed out and the monitoring reported half the machines as down. All were running. The redirect was removed. False negatives hide outages. False positives destroy confidence in the monitor, which is worse.

Where to start

The order matters more than the tools.

  1. One read-only report on a schedule, delivered where the operator already looks. Contact gaps, unanswered messages, renewals due next month. No writes.
  2. One queue with a boundary. A list of small tasks and a place the agent must stop. A first automation should not both decide and act.
  3. One deterministic check, monthly. Permissions, expiry dates, backups, open ports. No model. It will still be correct in a year.

After that, the tier test applies. Where a cheap mechanical check proves the result, a task can run unattended. Where none exists, the task prepares a decision.
