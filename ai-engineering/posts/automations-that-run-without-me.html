The hard part of running 11 AI agents was management

A status board reported that seven of 10 agents had failed. All were working. The error was not in the monitoring code, and it was not the last failure of its kind.

By Nicholas Garcia — Lecturer, NUS School of Computing · Deputy Director, NUS FinTech Lab

Disclosure: the systems described here belong to the author, who built and operates them. This account is drawn from their configuration files, design documents and incident records.

A status board watching a fleet of automated agents reported one morning that seven of the 10 then running were broken.

All 10 were running normally. Several were doing precisely what they had been built to do, which was to find and report problems elsewhere on the machine.

The board was reading each agent's log and asking a single question — did this run succeed — but the code answering it had quietly collapsed two different questions into one. It treated an agent that reported bad news as an agent in a bad state. A monitoring agent listing six failed services was marked as failing. So was a security auditor that flagged a loose file permission, and a cost controller that reported a budget overrun.

"A role that finds problems is a role doing its job," the system's design notes now read, in a section added after the incident. "The health of the employee is not the health of what it watches."

That correction is a sentence about management, not about software. It is also representative. Across roughly a year of running a small fleet of scheduled AI agents, the failures that cost real time have almost all been organizational: misread performance signals, starved priorities, missing chains of command and alert fatigue. The technical problems were comparatively easy.

That pattern is the subject of this account, because it is the part that transfers. The specific tools will be obsolete within two years. The management failures are the same ones that afflict human teams, arriving faster and in writing.

The fleet

The system runs on one small cloud server and a Mac. There is no platform team. Most of the code is Python from the standard library, scheduled by cron, with a language model called a handful of times a day.

Seven of the 11 use no language model at all. They parse logs, compare file permissions against expectations, count pending updates and read a spending ledger. The four that do call a model carry a per-run spending limit and record what each run cost.

Every agent obeys the same first rule: observe and propose, do not act. An agent reads, analyzes and files findings. It does not edit code outside its own directory, send outward communication or spend money. Corrections travel through an issue tracker, where a person or a separate overnight worker implements them.

The break point was about eight

Below roughly eight agents, a list is sufficient. Past that point, three problems arrive together.

The first is memory. It becomes genuinely difficult to recall what each job was built to do, and the code does not say.

The second is the one described above. Without a defined difference between a failing agent and an agent reporting failure, the status signal is worthless in both directions.

The third is that agents accumulate questions with nowhere to send them. A job that encounters a decision it cannot make has only two options in an ordinary design: guess, or stop. Both are bad, and the second is invisible.

The response was an org chart. Each agent now carries a job title, a named manager, a required run frequency and a charter of one sentence, all in a version-controlled file. The titles are conventional: chief of staff, managing editor, creative director, knowledge gardener, staff quality engineer, fleet health officer, security auditor, cost controller, release gatekeeper.

The charters are written as job descriptions. The managing editor "holds the standard of excellence for everything the firm writes and returns work that is not good enough," according to its entry. The creative director "keeps Nick's public output on voice and on brand."

Those sentences do practical work. When a new task arrives, the charter decides which agent takes it, and the decision takes seconds instead of an architectural argument.

Giving agents a way to ask

The component that has proved most valuable is also the least technical. Any agent can file a question addressed to its manager, then keep working.

Three constraints make it usable. A question is limited to one sentence and 400 characters, and longer text is rejected. Unknown senders and recipients cause an error rather than creating a question nobody owns. And a repeated question, normalized for spacing and capitalization, returns the existing record rather than filing a duplicate, so an agent that runs daily can call the command every single run without flooding anyone.

Unanswered questions rise. A sweep runs twice a day and moves anything older than 48 hours one level up the chart, one level per sweep, never two. Questions that reach the top generate a single message to a phone. Nothing escalates past the person at the top; it simply stays open.

The effect is the one a functioning organization produces. A creative director's question about an essay goes to the managing editor, and becomes the owner's problem only if the editor has not resolved it in two days. Fewer questions arrive than a flat design would produce, and the ones that do are the ones nobody else could answer.

Four failures, read as management problems

A priority system that starved its own priorities. Items marked as explicit directives kept losing to routine scoring, so urgent work never ran. The fix was to make the priority increase additive rather than multiplicative, and to add a manual override that ignores quiet hours. The override had to be applied in two separate gates. Only one was corrected on the first attempt, which delayed the fix by several days.

A loop that ran for seven hours on missing code. A refactor deleted the scripts a running loop depended on. The loop did not stop. It failed and restarted for about seven hours overnight, consuming budget and filling the logs, because nothing verified that the target still existed before invoking it. A pre-flight check and a restart counter now trigger the kill switch.

A control that was assumed rather than verified. A draft page was published to a static host on the assumption that an unlisted page is a private page. It is not. Anyone with the address can read it, and a catalog link makes the address public. The page was removed on an emergency basis. A continuous integration check now fails any change that places a hidden page in the published directory.

Forty-two hours of false alarms. A routing change began intercepting connections and holding them open. Remote checks timed out, and the monitoring reported half the machines as down. All were running. False negatives hide outages. False positives destroy confidence in the monitor, which is the more expensive outcome.

Three of those four are failures of organization rather than engineering. Priorities that do not reach the work. A control assumed to exist. A monitor that lost credibility. Only the crash loop is a straightforward coding defect, and even that one is a failure to define what a completed run means.

Alert fatigue is the constraint

The design decision that most improved the system was reducing how often it speaks.

The security audit originally ran daily. That was wrong. Its checks rarely change, and a report identical 30 times a month stops being read, which means the report that differs is skimmed as well. It now runs monthly and sends a message only when a check fails. Silence carries information.

Every agent is capped at five new issues per run, with a duplicate search first. The activity digest on the status board classifies entries by default as routine, on the stated principle that being wrongly quiet is better than being wrongly loud. Report summaries are extracted by a fixed set of rules, and when no rule fits, the summary is left blank rather than guessed, because an incorrect summary is worse than none.

Each of those is a choice to generate less output from a system capable of generating far more. In a fleet with one reader, attention is the scarce resource, and every design decision is ultimately a decision about how to spend it.

What transfers

Organizations deploying autonomous agents at larger scale will meet these problems earlier and harder than the technical ones, for a simple reason: the technical problems have vendors and the management problems do not.

Four questions are worth answering before an agent is put on a schedule.

Can the system tell a failing agent from an agent reporting failure? If not, the status display will be wrong in both directions, and confidence in it will not survive the first false alarm.

Where does an agent send a question it cannot answer? An agent with no escalation path will either guess or stop silently, and stopping silently is the more damaging of the two.

What is the cap on output? An agent with no ceiling on issues, alerts or messages will exhaust its reader's attention, after which the system is unmonitored whether or not it is running.

Which controls are assumed rather than tested? The draft that went public was protected by a control that had never existed. That class of error is invisible until it is expensive.

Limits of this account

This is one operator's experience with 11 agents over about a year. It is not a study, there is no control group, and nothing here should be read as a finding about enterprise deployments at hundreds of agents, where coordination costs are likely to differ in kind rather than degree.

The scale is also modest by design. The agents are restricted to observing and proposing, which removes a category of failure that larger deployments will have to confront directly.

What the account does support is a narrower claim. The limiting factor on a small autonomous fleet was not model capability, and was not the difficulty of writing the jobs. It was the absence of the ordinary structures that any group of workers requires: a definition of the role, a way to escalate, an honest performance signal and a limit on how much anyone may say.
