An org chart for 11 software agents

Each scheduled job carries a job title, a manager and a charter. A command-line tool lets any agent ask its manager a question, and unanswered questions rise one level every 48 hours until they reach a person.

By Nicholas Garcia — Lecturer, NUS School of Computing · Deputy Director, NUS FinTech Lab

Part of 16 scheduled jobs run without supervision.

Eleven automated jobs on one server now operate under a formal org chart. Each carries a job title, a named manager, a charter of one sentence and a required run frequency, all stored in a version-controlled configuration file.

The chart was not the original plan. It was added after the number of scheduled jobs passed eight and three problems arrived together: no reliable record of what each job was for, no way to distinguish a broken job from a job reporting bad news, and no path for a job to raise a question.

The chart

The file holds 12 nodes — one person and 11 agents.

nick                  CEO (human)
└── co-ceo-engine     Chief of Staff
    ├── auto-editor   Managing Editor
    │   ├── auto-brand        Creative Director
    │   ├── auto-chronicler   Chronicler
    │   └── auto-librarian    Knowledge Gardener
    ├── auto-qa       Staff QA Engineer
    │   ├── auto-sre          Fleet Health Officer
    │   └── auto-security     Security Auditor
    ├── auto-controller       Cost Controller
    ├── signal-watch          GTM Signal Watch
    └── merge-warden          Release Gatekeeper

Each entry records the manager it reports to, the directory it owns, the location of its log, the location of its reports, how often it must run, how many hours may pass before it is considered stale, and a charter.

The charters are written as job descriptions. The managing editor "holds the standard of excellence for everything the firm writes and returns work that is not good enough." The creative director "keeps Nick's public output on voice and on brand."

Those sentences settle scope disputes faster than architectural argument. When a new task arrives, the charter determines which role takes it.

Two commands support the file. One prints the tree. The other validates the chart and exits with an error on any problem, including an unknown manager, a cycle in the reporting lines or a missing directory.

Agents that ask questions

The questions mechanism is the component that has proved most valuable.

A role that reaches a decision it cannot make files one question and continues working. It does not wait for an answer, and it does not resolve the problem by acting outside its own directory.

orgctl ask --from auto-brand \
  --text "Should the Friday essay lead with the cost number?"

orgctl ask --from auto-editor \
  --text "Ship the draft as-is or hold it for a fact check?" \
  --context "reports/brand-2026-08-08.md" \
  --option "Ship it" --option "Hold for fact check"

orgctl ask --from auto-sre --to nick \
  --text "Disk is at 91 percent. Do I open a p1?"

The recipient defaults to the sender's manager, so most calls omit it. The third example deliberately skips a level, which is permitted.

Three rules make the command safe to call from an automated job.

An unknown sender or recipient exits with an error. Identifiers must match the chart, so a typo fails at the source rather than creating a question nobody owns.

Question text is limited to one sentence and 400 characters. Longer text is rejected. This single limit does more than any other rule to keep the queue readable on a phone.

Repeated questions are safe. The same role asking a near-identical question, with whitespace and case normalized, while an earlier question remains open and less than 24 hours old, returns the existing identifier and appends nothing. A daily job can therefore call the command on every run without flooding the recipient.

Supporting commands list open questions, list questions awaiting a specific person, record an answer, withdraw a question and report per-role status.

The ledger is an append-only file, one record per line, never committed to version control. Answers, withdrawals and escalations all work by appending a record that supersedes earlier state. Withdrawing twice has no effect. A withdrawn question stops counting as open, never escalates and never blocks a later identical question.

The escalation sweep

A sweep runs twice a day. It moves any question unanswered for more than 48 hours one level up the chart.

The sweep moves a question one level at a time, never two. It is idempotent within the window, because the clock restarts at the last move, so a second sweep on the same day changes nothing.

A question already held by the person at the top never escalates further. It stays open, and the sweep records it as at-root.

When a question reaches the top, the sweep sends one message to a phone. That is the only outward action in the component, and it tolerates failure: if the messaging service is unavailable, the sweep logs the problem and exits successfully.

In practice, a creative director's question about an essay reaches the managing editor first and becomes a person's problem only if the editor has not resolved it within two days.

A status field that meant two things

A private page renders the chart with a status card for each agent. An early version of that card was wrong in a way worth documenting.

The status field answers one question: did this run fail. It does not answer what the run found.

An agent that finds problems is an agent doing its job. The fleet health officer reporting six services down is a healthy fleet health officer. The health of an agent is not the health of what it monitors.

Conflating the two reported that seven of 10 agents were broken. None were. The error also destroyed the signal for the case in which one genuinely fails.

The card now carries three states.

StateMeaningExamples
GreenThe run completed.Findings of any number, a flagged verdict, a spending figure, duplicates skipped.
AmberThe run completed in a reduced mode.A spending limit that truncated the work, an unreachable source, a model step that failed and was skipped, a code push deferred to the next run.
RedThe run stopped partway.No completion marker, an unhandled exception, a push failure that ended the run.

Two rules keep the red state honest. Both were added after red cards appeared beside log lines that reported success.

A completion marker takes precedence. If a role logged that its run finished, the run finished by its own account, and nothing may then classify it as failed. A hard error logged during that run becomes the amber reason instead.

A deferred push is not lost work. A push failure that the role marks as retryable, or as left for the next run, is a postponed step; the content arrives on the following run. A push failure the role does not mark that way still ends the run and remains red.

Most apparent failures in a fleet of this kind are postponed steps rather than lost work. Systems that do not encode the difference generate morning investigations into problems that have already resolved themselves.

Turning a log into a phone-readable digest

The second half of the status card summarizes recent activity. The command-line tool performs all extraction. The page renders what it receives and parses nothing.

Five rules produce the digest.

Continuation lines fold into their neighbors. A line with no timestamp belongs to an adjacent entry — forward when the next entry is a version-control line, backward otherwise. A line that cannot be dated is dropped, so no entry renders as unknown.

Consecutive repeated lines collapse into one entry with a count.

Every entry is classified as an outcome, a finding, an error or plumbing. The default is plumbing, on the principle that being wrongly quiet is better than being wrongly loud.

Structured lines are mined. Several roles log machine-readable data. Issue addresses, titles and counts are extracted into entries, and the raw data never reaches the page. Unreadable data degrades to a single truncated entry rather than causing a failure.

The digest is capped at 10 entries, newest first, with one guard. If the newest 10 are all plumbing while the same run produced findings, substantive entries take half the slots. The fleet health officer ends every run with five deduplication lines, a push and a notification; without the guard, its six actual down verdicts fall off the end and the card reports nothing.

Two further rules emerged from real logs. Test residue never leads: a line carrying a dry-run marker cannot be classified as an error and is excluded from every source the headline draws on. An agent whose last run was a dry run reports nothing rather than presenting residue as work.

And an incorrect summary is worse than none. Report headlines are extracted by a short list of ordered rules tested against real reports from every role. When no rule fits, the headline is empty and the page renders nothing in its place.

When a chart is warranted

Three scheduled jobs do not need an org chart. A list is sufficient.

At roughly eight jobs, the three problems described above arrive together. The chart addresses all three with about 1,500 lines of standard-library Python and a configuration file.

The cost is an additional artifact to keep accurate. That is why the validation command exists and why no role receives a schedule before it has a row in the chart. An org chart that has drifted from reality is worse than none, a finding that also applies to the human version.
