The Bot That Reads Its Own Transcripts

My assistant runs a daily loop that mines friction out of its own session logs, proposes exactly one change, gates it on a runnable check, and halts itself when the changes stop helping.

By Nicholas Garcia — Lecturer, NUS School of Computing · Deputy Director, NUS FinTech Lab

Part of Sixteen Automations That Run Without Me.

I have a personal assistant bot on Telegram. It is a coding agent with a chat front end, locked to my account, and it can read my mail, check my calendar, look things up and run things on the server.

Like every assistant, it was mediocre in specific, repeated ways. I would ask for something and get the wrong shape of answer. A tool would fail the same way three times in a week. I would correct the same misunderstanding on Monday and again on Thursday.

The obvious fix is to sit down and improve the instructions. I did that a few times and it did not stick, because by the time I sat down I could not remember what had annoyed me.

So I built a loop that remembers for me. Every day it reads the bot's own session transcripts, finds the friction, and proposes one improvement.

Where the data comes from

This is the part I like most, and it needed no new instrumentation at all.

The bot is a coding agent, and coding agents already write full session transcripts to disk as JSONL. Every message, every tool call, every error. A state file maps each chat to its session id. That is a complete record of every interaction I have ever had with the assistant, sitting there unused.

The mining step reads recent transcripts and extracts four kinds of friction signal:

  • Corrections — me telling it that what it just did was wrong.
  • Tool errors — something it tried to call that failed.
  • Unfulfilled requests — I asked, it did not deliver.
  • Re-asks — me asking the same thing again, which is the strongest signal of all because it means the first answer was useless enough that I bothered to retype it.

Candidates get scored and deduplicated by theme, so twenty instances of the same annoyance become one candidate with a high score rather than twenty low-value ones.

If transcript friction comes back empty — which happens on a quiet week — the cycle falls back to a second miner that reads the themes I have been writing and talking about, so there is usually something to work on. I am ambivalent about that fallback. Doing nothing is a perfectly good outcome for a self-improvement loop, and I have caught it working on something mildly useful when the honest answer was "nothing is wrong this week".

One change per cycle

The proposal step takes the top candidate and derives one concrete improvement plus a runnable check — a command that exits zero if the change did what it claimed.

One is a hard limit and it is doing real work. A loop that proposes five changes at once cannot attribute the result to any of them, which means the ledger below becomes noise and the halt condition never fires correctly.

This step is also the only place a model's judgement enters the loop. Everything else — mining, gating, the ledger — is deterministic Python, which means the self-test can run the whole cycle end to end with a stub in that one seam and no network access at all.

The gate: what it may change alone

The check runs. If it passes, the change is classified.

Auto-applied, because it is safe and reversible:

  • Clarifications to the bot's instruction file, written into a marked block so I can see exactly which lines the loop wrote.
  • Proposals for new read-only tools.
  • Notes about skills and recurring errors.

All of it lands as a git commit, so undoing anything is one revert.

Escalated to me, never auto-applied:

  • Anything touching outbound email.
  • Calendar writes.
  • The allowlist of who may talk to the bot.
  • Anything destructive.

Those get queued and pinged to me on Telegram for explicit approval. The boundary is not "is this a big change" — it is "can this reach another human or lose data". A one-line tweak to the mail-sending path is escalated; a substantial rewrite of a read-only summarisation prompt is not.

Two more constraints. Tool and skill ideas land in a proposals directory rather than blindly editing the live tools. And the loop never restarts or redeploys the running bot. Instruction changes are picked up on the next message anyway; anything needing a deploy waits for me. A self-improving system that can hot-restart itself can also hot-restart itself into a state where it cannot be fixed.

The ledger, and knowing when to stop

Every cycle appends to a ledger: what was changed, what the check returned, and — the important column — did the friction actually drop in the following period.

That third column is the entire difference between a self-improvement loop and a change-generation machine. Without it you have a system that is enthusiastically doing things, and no evidence that any of them helped.

The reflection step reads the ledger, finds the peak, flags regressions, and halts the loop after a run of cycles that made things worse. There is a command that just prints its verdict.

The halting condition matters more than I expected. The natural failure mode of a loop like this is not a catastrophic bad change — the gate catches most of those. It is slow accretion: a hundred small clarifications added to an instruction file over six months, each individually defensible, collectively turning a crisp set of instructions into a swamp. The loop is written so that it declines by adding — so the halt has to be explicit, measured against whether friction actually fell.

It converges in one of two ways. Either there is no friction left to absorb and a cycle comes back empty, or reflection halts it on decline.

The self-test is the deliverable

There is one command that runs the whole cycle end to end with no side effects and exits zero. No network, no git writes, no messages sent. It uses the deterministic stub in the judgement seam.

I treat that command, not the loop, as the thing I built. The loop is allowed to modify a live assistant's instructions on a daily schedule. I am not installing that on a timer on the strength of having read the code.

It runs daily, early in the morning, on the server, with its own log. I review the ledger and the escalation queue every few weeks.

What I would tell someone copying this

  1. Your agent's transcripts are already the dataset. You probably do not need to instrument anything. Look at what your tooling writes to disk.
  2. Re-asks are the best signal. Corrections are noisy and tool errors are often environmental. Someone retyping a request means the first answer was worthless.
  3. One change per cycle, or you cannot attribute the outcome.
  4. Gate on a runnable check, not on confidence.
  5. Split on reach, not on size. Can this touch another human, or destroy something? Escalate. Otherwise, let it commit and rely on revert.
  6. Record whether it actually helped, and let the loop stop itself. This is the step everyone skips, and it is the one that separates improvement from churn.
