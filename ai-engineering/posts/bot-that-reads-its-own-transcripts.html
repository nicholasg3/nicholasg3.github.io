An assistant that mines its own transcripts

A daily loop reads the assistant's own session logs, extracts four kinds of friction, proposes a single change, verifies it with a runnable check and stops itself when the changes stop helping.

By Nicholas Garcia — Lecturer, NUS School of Computing · Deputy Director, NUS FinTech Lab

Part of 16 scheduled jobs run without supervision.

A personal assistant bot running on a chat service improves itself each morning by reading its own session transcripts. The loop extracts friction, proposes one change, verifies the change with a runnable check and records whether the change helped.

The assistant is a coding agent with a chat front end, restricted to one account. It reads mail, checks a calendar, looks up information and runs commands on a server.

Its weaknesses were specific and repeated. Requests returned the wrong shape of answer. A tool failed the same way several times in one week. The same misunderstanding required correction twice in four days.

Manual instruction edits did not resolve this. By the time the operator sat down to make them, the specific annoyances had been forgotten. The loop was built to record them instead.

The data already existed

The source required no new instrumentation.

Coding agents write full session transcripts to disk as structured text — every message, every tool call, every error. A state file maps each chat to its session. That constitutes a complete record of every interaction with the assistant.

The mining step reads recent transcripts and extracts four kinds of friction signal.

  • Corrections: the operator states that the last action was wrong.
  • Tool errors: a call the assistant attempted and failed.
  • Unfulfilled requests: a request that produced no delivery.
  • Repeated questions: the same request typed again. This is the strongest signal, because it indicates the first answer was useless enough to justify retyping.

Candidates are scored and deduplicated by theme, so 20 instances of one annoyance become a single high-scoring candidate rather than 20 low-value ones.

When transcript friction is empty, which happens in quiet weeks, the cycle falls back to a second miner that reads recent written themes. That fallback is questionable. Doing nothing is a valid outcome for a self-improvement loop, and the fallback has produced marginal work in weeks when the correct answer was that nothing was wrong.

One change per cycle

The proposal step takes the highest-scoring candidate and derives one concrete improvement and one runnable check — a command that exits successfully if the change accomplished what it claimed.

The limit of one is enforced. A loop that proposes five changes at once cannot attribute the result to any of them, which makes the ledger useless and prevents the halting condition from firing correctly.

This step is also the only point at which model judgment enters the loop. Mining, gating and the ledger are deterministic code. The self-test can therefore run the entire cycle with a fixed substitute at that one point, without network access.

What the loop may change alone

The check runs, and a passing change is classified.

Three categories are applied automatically because they are safe and reversible: clarifications to the assistant's instruction file, written into a marked block; proposals for new read-only tools; and notes about recurring errors. Each lands as a version-control commit, so reversal is a single command.

Four categories are escalated to a person and never applied automatically: anything affecting outbound email, calendar writes, the list of who may contact the assistant, and destructive operations. These are queued and sent to a phone for explicit approval.

The dividing line is reach, not size. A one-line change to a mail-sending path is escalated. A substantial rewrite of a read-only summarization prompt is not.

Two further constraints apply. Tool and skill proposals are written to a proposals directory rather than modifying live tools. And the loop never restarts or redeploys the running assistant. Instruction changes take effect on the next message; anything requiring deployment waits for a person.

A self-improving system able to restart itself is also able to restart itself into a state from which it cannot be repaired.

The ledger and the halting condition

Each cycle appends a record: the change made, the result of the check and whether friction decreased in the following period.

That third field distinguishes a self-improvement loop from a change-generation machine. Without it, the system produces activity and no evidence of benefit.

The reflection step reads the ledger, identifies the peak, flags regressions and halts the loop after a run of cycles that made conditions worse. A separate command prints its verdict.

The halting condition matters more than expected. The characteristic failure is not a single damaging change, which the gate catches. It is accumulation: a hundred small clarifications added to an instruction file over six months, each defensible on its own, collectively turning a concise document into an unusable one. The loop is designed to decline by adding, so the halt must be explicit and measured against whether friction actually fell.

The loop converges in one of two ways. Either no friction remains and a cycle returns empty, or reflection halts it on decline.

The self-test is the deliverable

One command runs the full cycle with no side effects and exits successfully. It makes no network calls, no version-control writes and sends no messages, using the fixed substitute at the judgment step.

That command, rather than the loop, is treated as the delivered artifact. The loop modifies a live assistant's instructions on a daily schedule, which is not a change to schedule on the strength of a code review.

It runs each morning on the server with its own log. The ledger and the escalation queue are reviewed every few weeks.

Six points for a similar build

  1. The transcripts are already the dataset. Existing tooling probably writes them to disk.
  2. Repeated questions are the strongest signal. Corrections are noisy, and tool errors are often environmental.
  3. One change per cycle, or attribution is impossible.
  4. Gate on a runnable check, not on stated confidence.
  5. Divide on reach, not size. Anything that can reach another person or destroy data escalates.
  6. Record whether the change helped, and allow the loop to stop itself.
