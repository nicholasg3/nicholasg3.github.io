MemoryAgents

Two memory stores, kept apart by design

One store holds rules. The other holds episodes. A write gate on the episodic store rejects rule-shaped entries and redirects them, and that separation is what keeps either store useful.

By Nicholas Garcia — Lecturer, NUS School of Computing · Deputy Director, NUS FinTech Lab

Part of 16 scheduled jobs run without supervision.

An agent fleet running on one server keeps its memory in two stores with separate write paths, separate lifecycles and a gate that prevents entries in one from reaching the other.

Single-store designs degrade in a consistent way. After several months the retrieved context mixes statements of fact about past events with imperative rules about future behavior, and the model treats both as equally binding descriptions of the present.

Those are different kinds of information. One records what happened. The other governs what happens next.

The rules store

Each lesson is one file. The identifier matches the filename. A short structured header precedes an optional body written for people.

---
id: git-add-own-files-only
tags: [git, doctrine]
trigger: One line — when this lesson applies.
rule: The imperative rule itself. Max 2 sentences.
evidence: issue URL, commit hash, or doc path.
created: 2026-08-11
last_applied: 2026-09-02
---

Optional body: the incident that produced the rule.

Six fields are required, and each serves a purpose.

Separating the trigger from the rule is the central decision. The trigger states when the rule applies; the rule states what to do. A store of imperatives without triggers is a set of context-free commands, and a model will apply them everywhere or nowhere.

The rule field is capped at two sentences. A lesson requiring a paragraph is not yet a lesson. The body exists for that paragraph, and the retrieval code never reads it.

Evidence is required: an issue, a commit or a document. Rules with no traceable origin should not govern agent behavior months later.

The last-applied date is updated when a lesson is cited, which produces a usage signal and an eviction order.

Four curation rules

The store is a library rather than a scheduled job. It has no schedule of its own. Readers pull from it and writers propose to it.

The active set is capped at 50 files. If promoting a candidate would exceed the cap, the proposal must name the file it would retire, defaulting to the least recently applied. A memory that grows without limit is one whose retrieval quality declines without limit.

Writers never touch the active set. The write path only ever adds to an inbox directory. Any job can therefore propose a lesson from a read-only reporting step without affecting what the fleet currently treats as authoritative.

Promotion is manual. A person, or an interactive session, moves a file from the inbox to the active set. The knowledge gardener role proposes; it cannot promote.

A contradiction check precedes any proposal. The gardener compares a candidate rule against the workspace's architecture map and decisions log, and flags a direct conflict in its report instead of proposing the rule. Two contradictory rules are worse than either alone, because the model then chooses between them.

Deduplication is by identifier. The write path refuses any candidate whose identifier already exists in either directory, so near-duplicates do not accumulate.

Retrieval ranks by tag-match count, then recency, and returns active lessons within a token limit. Citation is a separate call that updates the last-applied date on the lessons actually used, because selecting a lesson is not the same as applying one.

Results are injected in three places: into spawned worker prompts, into the engine's per-cycle context and into interactive sessions.

The episodic store

The second store records what happened, what was decided and why. It has its own command-line tool, and the bridge to it never writes the store directly. All writes pass through that tool, so the storage format is not the bridge's concern.

The read path accepts tags or a context string and returns a token-limited block ready for a prompt. It cannot write: it never calls any modifying command.

The write path is primarily a quality gate. It accepts an entry only if the entry is an event or a decision accompanied by a reason, is not trivial, is not a near-duplicate of a recent entry and is not rule-shaped.

The final condition is the load-bearing one. An entry that is imperative and general — shaped like a rule rather than an event — is rejected, and the rejection points to the rules store's write path.

Without that gate the two stores converge within weeks. A rule gets written to the episodic store because the write is cheap and the store is available, and the same guidance then exists in two places under two lifecycles. The capped, curated, contradiction-checked store is no longer authoritative.

Capturing episodes automatically

The episodic store has a capture problem the rules store does not. Rules are written when something goes wrong, which is memorable. Episodes occur during ordinary work, which is not.

Three mechanisms write to it. The engine saves at the end of every cycle, on both the memo-worthy and the not-memo-worthy paths, limited to a few saves a day through a lock-serialized counter.

Interactive sessions use a turn-end hook. An earlier design captured at session end, which does not work, because closing a laptop generates no event. A hook on every turn end with a time-based delay does work. The delay file is written the moment a checkpoint comes due, before the capture runs, so a failure during capture cannot produce a loop.

A daily write cap applies, because the failure mode of automated capture is a store filled with routine entries of no value.

The operating principle is short. Determine whether each item is a rule or an episode, store them in separate places, and make writing one into the other mechanically impossible. The remaining design questions are easier once the two are not in conflict.
