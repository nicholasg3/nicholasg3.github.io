Two Memory Stores That Are Not Allowed to Overlap

One store holds rules, the other holds episodes. The write gate on the episodic one rejects rule-shaped input and points it at the other store. Keeping them separate is most of what makes either of them useful.

By Nicholas Garcia — Lecturer, NUS School of Computing · Deputy Director, NUS FinTech Lab

Part of Sixteen Automations That Run Without Me.

Every agent memory system I tried first was one big store. Write things into it, retrieve things out of it by similarity, inject the results into the prompt. They all degrade the same way: after a few months the retrieved context is a mix of "we decided to use the API rather than IMAP last August" and "never run git add -A in this repo", and the model treats both as equally binding facts about the present.

Those are different kinds of thing. One is a fact about what happened. The other is a rule that should govern what happens next. My fleet now keeps them in two stores with different lifecycles, different write paths and a gate that stops one leaking into the other.

The rules store

One file per lesson. A kebab-case id matching the filename, a short frontmatter block, and an optional body for humans.

---
id: git-add-own-files-only
tags: [git, doctrine]
trigger: One line — when this lesson applies.
rule: The imperative rule itself. Max 2 sentences.
evidence: issue URL, commit hash, or doc path.
created: 2026-08-11
last_applied: 2026-09-02
---

Optional body: the incident that produced the rule.

Six required fields, and every one of them earns its place.

trigger separate from rule is the design decision I would defend hardest. The trigger says when this applies; the rule says what to do. A store of imperatives with no triggers is a store of context-free commandments, and a model will apply them everywhere or nowhere.

rule is capped at two sentences. A lesson that needs a paragraph is not a lesson yet, it is an unfinished thought. The body exists for the paragraph, and the selector never reads the body.

evidence is required — an issue, a commit, a document. No anonymous folk wisdom. If nobody can point at what produced a rule, it should not be governing an agent's behaviour six months later.

last_applied is updated by the selector when a lesson is actually cited, which gives you a usage signal and, eventually, an eviction order.

Four rules about curation

The store is a library, not a daemon. It has no schedule of its own; readers pull from it and writers propose to it.

  1. The active set is capped at 50 files. Hard cap. If promoting a new lesson would exceed it, the proposal must name what it would retire, defaulting to the least-recently-applied. A memory that grows forever is one whose retrieval quality falls forever.
  2. Writers never touch the active set. The emit path only ever writes to an inbox directory. This means any daemon can propose a lesson from a read-only reporting step without any risk to what the fleet currently believes.
  3. Promotion is manual. A human, or an interactive session — never a background daemon — moves a file from the inbox to active. The Knowledge Gardener role can propose; it cannot promote.
  4. Contradiction check before proposal. The gardener checks a candidate rule against the workspace's architecture map and decisions log for a direct contradiction and flags it in its report instead of proposing it. Two rules that contradict each other are worse than either one alone, because now the model picks.

Deduplication is by slug: the emit path refuses to write a candidate whose id already exists in either directory. You update the existing file by hand rather than accumulating near-duplicates. This is blunt and it works.

Reading is a selector call with tags, ranked by tag-match count then recency, token-bounded, active lessons only. There is a separate citation call that updates last_applied on the lessons you actually used — deliberately not the same call as selection, because selecting a lesson is not the same as applying one.

The results get injected in three places: into spawned worker prompts, into the engine's per-cycle context, and into interactive sessions.

The episodic store

The other store holds what happened, what was decided, and why. It has its own CLI, and my bridge to it never writes the store directly — it goes through that tool's own command, which means the store's format is never my problem.

The read path takes tags or a context string and returns a token-bounded, prompt-ready block. It is structurally incapable of writing: it never calls any of the mutating commands.

The write path is the interesting one, because it is mostly a quality gate. It accepts a memory only if it is:

  • an event or a decision with a reason,
  • not trivial,
  • not a near-duplicate of something recent,
  • and not rule-shaped.

That last condition is the whole point of this post. If you try to save something imperative and general — the shape of a rule rather than the shape of an event — the gate rejects it and points you at the other store's emit path.

Without that gate, the two stores converge within weeks. Somebody writes a rule into the episodic store because it is right there and the write is cheap, and now the same guidance exists in two places with two lifecycles, and the capped, curated, contradiction-checked rules store is no longer the authority on anything.

Capturing episodes without remembering to

The episodic store has a capture problem the rules store does not. Rules get written when something goes wrong, which is memorable. Episodes need capturing during ordinary work, which nobody remembers to do.

Three things write to it. The engine saves at the end of every cycle, on both the memo-worthy and not-memo-worthy paths, rate-limited to a few saves a day through a lock-serialised counter.

Interactive sessions use a turn-end hook. My first design captured at session end, which does not work: closing a laptop lid fires no event. A hook on every turn end with a time-based debounce does work, and the debounce file is touched the instant a checkpoint comes due — before the capture runs, not after — so a crash mid-capture cannot cause a loop.

And there is a cap on writes per day, because the failure mode of automated capture is a store full of "ran the tests, they passed".

If you are building agent memory and you take one thing from this: decide whether each thing you are about to store is a rule or an episode, put them in different places, and make it mechanically impossible to write one into the other. Everything else about memory design is easier once those two are not fighting.
