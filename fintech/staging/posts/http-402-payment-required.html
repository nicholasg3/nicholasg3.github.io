The web reserved a payment code in 1991. We still bolt money on later.

HTTP 402 Payment Required still exists in the protocol. The fact that online commerce mostly ignores it is a story about path dependence in payment infrastructure.

Seed tweet

The claim

HTTP defined status code 402 as “Payment Required.” It remains reserved for future use in current HTTP semantics. That is not a conspiracy. It is a fossil of an unfinished internet money design.

Every checkout that redirects to a processor, every wallet popup, every card form is evidence that value transfer never became a first-class browser primitive the way hyperlinks did.

What the standard actually says

RFC 9110 documents 402 Payment Required and notes it is reserved for future use. The protocol left a door. Industry did not walk through it in a standardized way.

Instead, payments evolved as application-layer products: card networks, banks, processors, and later wallets and crypto rails. Those products optimized for risk, chargebacks, identity, and regulation — problems a bare status code never solved.

Why the fossil matters now

Agentic commerce and machine-to-machine payments revive the old dream: machines that can request and settle value without a human filling a form. The protocol gap becomes a product opportunity again.

But the hard problems remain authorization, dispute, fraud, sanctions, and who is the customer of record. A 402 response does not answer those. Fintech founders who market “native internet money” without an authorization model are selling nostalgia for a missing standard.

What to do

If you design agentic payments, write the authorization and revocation path before the protocol romance. Who can spend, on what limits, with what audit trail, and how a human stops it.

Use 402 as a teaching artifact for path dependence — not as proof that a simple header will replace Visa.
