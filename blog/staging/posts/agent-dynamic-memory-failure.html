Static demos hide dynamic memory failure

Agent failure on dynamic memory tasks

The claim

Agents that look competent in static demos can fail when memory is dynamic: goals change, tools change, prior beliefs expire.

Evaluate on tasks where the right answer depends on updating memory, not replaying a frozen plan. If your eval never invalidates old context, you are not testing agents. You are testing autocomplete.

What “dynamic memory” means here

Static demos give the agent a fixed brief and a fixed world. The ticket does not change. The API schema does not change. Yesterday’s “customer is on plan A” remains true. Success is pattern completion over a stable prompt.

Dynamic memory tasks break that stability on purpose. Midway through a run, the goal is revised. A tool returns a new error shape. A policy exception expires. A user corrects a fact the agent stored two steps ago. The correct next action depends on noticing the change and revising state, not on continuing the original plan with more confidence.

That is closer to production. Production is full of revised tickets, rotated credentials, and customers who change their mind after the agent has already “remembered” the wrong thing.

Why demos look better than systems

Demos optimize for a clean arc: problem, tools, solution, applause. The context window is curated. Failures that would require forgetting are edited out. Eval harnesses often reward final-answer match on fixed benchmarks. Nothing in the score asks whether the agent discarded a stale belief when the world moved.

So teams ship agents that ace frozen tasks and then surprise themselves in live ops. The gap is not always model size. It is often eval design that never made invalidation a first-class event.

A concrete scene

An agent is told to migrate a service using config version 3. Midway, an operator marks version 3 as deprecated and points to version 4. A strong dynamic agent reloads state, re-plans, and continues against version 4. A weak one finishes a beautiful migration to a dead target, citing the original brief with perfect fluency.

On a static eval, both might look fine if the harness never injects the deprecation. On a dynamic eval, only one is competent.

How to evaluate properly

Build tasks where success requires update, not recall alone:

  • Inject goal changes after the agent has started acting.
  • Invalidate stored facts and score whether the agent stops using them.
  • Swap tool schemas mid-run and require re-discovery.
  • Reward correct abandonment of a plan, not only plan completion.
  • Log which memory entries were written, read, and superseded.

If your dashboard never shows “agent correctly forgot X,” you are not measuring memory. You are measuring persistence of the first story the model told itself.

Closing

Static demos hide dynamic memory failure. Treat that as a product risk, not a footnote. Until your evals invalidate old context on purpose, you are grading autocomplete in a costume. Agents that must live in changing systems deserve harder tests — and less credit for smooth runs through a frozen world.
