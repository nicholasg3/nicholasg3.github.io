Best practices need a repo

Agentic-agent development best practices

Seed tweet · source: W26 skill S=0.9

The claim

Expert agent-development guidance is valuable when it is concrete about tools, reviews, and failure modes. Lectures without operating constraints become content, not practice.

Pair any best-practice memo with a repo that implements it. If it cannot be checked out, it is not yet a practice.

Why advice dies on the slide

Agent development advice spreads as threads, conference talks, and “how we work at X” decks. The useful parts are usually narrow: how they structure prompts, which tests gate a merge, what the agent is forbidden to touch, how they recover when a loop burns tokens and does nothing.

Those details do not survive a paraphrase. “Always add review” is not a practice. “Every agent PR needs a human who owns the merge and a CI job that runs the integration suite the agent cannot skip” is closer. The second sentence can be written as a branch protection rule. The first cannot.

When guidance is only spoken, each team invents its own half-implementation. People remember the vibe of senior craft and lose the harness that made craft reliable.

A concrete scene

Two teams watch the same senior engineer walk through agentic coding. Both leave with the same notes: small tasks, tight feedback loops, aggressive tests. Team A pastes the notes into a wiki. Team B opens a repository with a sample agent config, a Makefile target for the eval suite, a CODEOWNERS file that names who may approve agent-authored diffs, and a short failure log of three past loops that went wrong and how they were stopped.

Three months later Team A is still “adopting agents.” Team B is shipping with a known failure budget. The difference was not inspiration. It was a checkout path.

What a practice repo must hold

A useful companion repo is not a product demo. It is a living constraint set. At minimum it should make the following easy to inspect:

  • How work is sliced into agent-sized units, including what is left human-only.
  • Which checks run before an agent change can land, and which ones the agent itself must not author.
  • How secrets, production credentials, and destructive tools are withheld.
  • What operators do when the agent is confidently wrong: stop conditions, rollback, and who gets paged.

If a memo claims a “review culture” but the repo has no merge rule, treat the memo as aspiration. If it claims safety but the sample agent can exfiltrate env vars, treat the memo as marketing.

How to use the lecture material

Industry lectures from strong product teams are still worth watching. Use them as hypotheses, not as inherited process. Extract one constraint at a time. Encode it. Run it on a real task for a week. Keep only what still earns its keep under your load, not under theirs.

Reject the idea that best practices arrive as complete playbooks from companies with different risk, staffing, and compliance. Import mechanisms. Re-measure outcomes.

Closing

Best practices for agent development are not a genre of writing. They are a genre of infrastructure. If someone offers you the former without the latter, ask for the repo. If there is none, you have a talk. You do not yet have a practice.
