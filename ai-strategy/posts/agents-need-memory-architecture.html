Agents Need a Memory Architecture

Production agents carry customer history, tool results, policy exceptions and multi-step plans from one session to the next. That experience usually lands in two places, prompt rules and model weights, which update on different schedules. Teams build both, seldom give them a joint owner, and find out about the gap when customers see the agent misbehave.

By Nicholas Garcia — Lecturer, NUS School of Computing · Deputy Director, NUS FinTech Lab

Large language model agents now keep experience across sessions: customer history, tool results, policy exceptions, multi-step plans. That forces a design choice most teams still file under implementation detail, which is where the agent remembers. Once that is settled, the rest follows fairly directly: each store gets an owner, and there is a rule for what happens when two stores disagree. Where the choice is skipped, owners and conflict rules are hard to assign later, because there is no agreed list of stores to assign them to.

This synthesis condenses a field study of public practitioner discourse into an argument operators can act on. When AI Assistants Remember: Memory as a Control Problem for Firms is still the checklist for controlling product memory. This piece comes a step before it and describes how memory problems form before any inventory can catch them.

When experience is written into prompts and into weights and nobody owns both, the two will drift apart. The architecture decision is about who owns that writing.

What We Studied

In a single archival harvest on 28 June 2026, the study collected 1,990 public rows about production agent memory from thirteen channels, including engineering blogs, standards material, practitioner newsletters, Reddit, Hacker News, Stack Overflow, YouTube, arXiv and conference notes. Screening for relevance left 100 coded deployment incidents. Thirty-five Tier-1 practitioner threads were coded in depth, backed by 106 deep-fetched quotes and 244 analytic memos. The method is constructivist grounded theory applied to digital field talk. The sample is public discourse, so it cannot stand in for a census of enterprise deployments.

Public forums over-represent builders who write about friction and under-represent regulated industries, which keep their failures private. The findings still carry weight because the same sequence appears across frameworks, cloud agents and custom stacks. Multi-step work creates pressure to retain experience, teams respond by building parallel stores, and those stores lose coherence as release velocity rises.

Two Places an Agent Can Remember

Production discussions centre on two storage modes. Both are legitimate, though neither covers the job on its own.

Prompt-layer memory can be read by people. Rules, system instructions, retrieved chunks and session summaries sit in repositories, prompt registries or vector stores that product teams can edit. If a billing agent must always ask for an account number first, that requirement is usually a rule in this layer, and a compliance officer can open it in git.

Weight-layer memory is statistical. Fine-tunes, preference training and distilled trajectories push patterns into parameters, which belong to machine-learning pipelines with slower release cycles. The same agent may "know" its billing habits without there being a single sentence anyone can open and inspect.

Trouble starts when the two layers are run as unrelated engineering surfaces. Prompt owners ship weekly and model owners ship quarterly, and neither team is responsible for checking that the rule still matches the weight. So when behaviour breaks, debugging means digging through two histories kept on two clocks. Recent technical work on learning experiential rules and policies jointly, and on co-failure ceilings in multi-model routing, describes the same split from the research side. Practitioners rarely cite those papers. They build the split anyway, under names such as session attributes, long-term memory servers and context engineering.

Three Episodes From the Field

Coding and constant comparison produced a process in three episodes. Operators can use them as a diagnostic sequence; they are analytic patterns, and no firm is bound to pass through them in order as a corporate lifecycle.

Episode Trigger Typical actors Failure signal
E1 · Retention pressure Agents must act across tools, turns, and sessions Application teams, model operators Demo resets; production needs institutional memory
E2 · Parallel stores Teams ship prompt rules, vector memory, and weight updates as separate projects Prompt engineers, platform ML, product No named owner of reconciliation
E3 · Coherence stress Stores evolve at different speeds under load Builders, platform, support Bugs that no single layer explains

Episode 1: Multi-step work demands memory

Practitioners give up on the single clever prompt once the job involves planning, tool calls and continuity across sessions. Reddit threads on production frameworks keep asking for "multi-step reasoning, tool calls, and memory," and describe planning loops that coordinate retrieval, tools and persistent context. In business terms, if the agent has to finish work a human would log in a ticket system, it needs state that outlives a browser tab.

Episode 2: Parallel systems without joint ownership

Next, teams add infrastructure: session attributes on cloud agents, middle layers between clients and vector databases, dashboards showing memory read and write history, and separate fine-tune pipelines for "how we usually handle this." Stack Overflow answers on session attributes treat conversation history as a bag of parameters, while engineering posts treat long-running work as a problem of preserving context. Each piece may be sound, but the result is several memory surfaces that nobody has reviewed as a single architecture.

Episode 3: Drift under production stress

As LangGraph-style agents or custom fleets scale, builders report hitting walls on session persistence, per-user memory and scoped context. Practitioner blogs recast the work as context engineering and urge product managers to take ownership of episodic, semantic and procedural layers. The field spends heavily on tooling and very little on institutional reconciliation, meaning a named role that settles the conflict when a prompt rule forbids a refund path that a fine-tuned policy still proposes.

For strategy, that gap is the main finding. Public discourse optimises persistence and observability first, and governance ownership comes later, often after an incident customers have already seen.

Two Mechanisms

Experience retention pressure. Production agents build up interaction histories, tool results and exceptions that demos throw away. When a workflow runs over days, retention becomes a design requirement.

Storage system mismatch. Human-editable rules and slower parameter updates have different owners, release cadences and audit trails. Session caches and vector stores sit between them as temporary glue, and without a reconciliation policy they settle in as permanent parts of the product.

What Operators Should Change

Before another memory product enters the stack, use the research as a screen for procurement and architecture. The table below sets out pass and fail signals for each row.

Screen Pass signal Fail signal
Store map Every memory class is listed: prompt rules, episodic cache, vector long-term, weights "The agent just remembers" with no inventory
Owner per store Named team for write rights, review, and delete or expire Product edits prompts; ML ships weights; nobody owns conflict
Reconciliation rule Documented precedence when rule and weight disagree Debug starts only after customer complaint
Release clocks Prompt and weight release calendars are visible together Independent deploys with no joint regression check
Audit path A reviewer can reconstruct why the agent acted from stores, not vibes Explanations stop at "the model said"
Stop rule Missing ownership or audit can pause scale-up More tools added to mask the split

Procurement should apply the same screen. Require vendors to separate memories that can be edited in prompts from those bound to parameters, to name how each can be inspected, and to document how conflicts are resolved. A performance demo that leaves those questions unanswered is incomplete for multi-step work.

Limits

The harvest is a single-month snapshot of English-language public discourse. The episodes are interpretive patterns drawn from constant comparison and are not frequency counts across every industry. Academic papers on rule-weight coupling and multi-model routing provide technical context but do not independently validate the field findings. The next tier of evidence would be longitudinal studies inside regulated firms.

Close

Agents that do real work will remember things, and that memory should be designed as an architecture with owners and reconciliation rules. The field talk already shows what happens otherwise: prompts, vectors and weights pile up by accident. Operators who map their stores, assign owners and set a stop rule before Episode 3 reaches customers will spend less time reconstructing behaviour they never designed.
